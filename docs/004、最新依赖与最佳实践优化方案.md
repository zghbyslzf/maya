# Maya CLI 最新依赖与最佳实践优化方案

## 概述

本文档基于 Rust 1.85+ (edition 2021)、clap 4.5、tokio 1.x、zip 2.6、rayon 1.10 等依赖库最新文档，对 Maya CLI 全部 8 个 crate + 5 个模块 + 集成测试进行全面审查，列出可优化点。

审查日期：2026-04-29

---

## 🔴 高优先级

### 任务 22：`compress_image` 中不必要的 `to_lowercase` 分配

**文件**：`crates/compress_pictures/src/lib.rs:157`

**问题**：`extension.to_string_lossy().to_lowercase()` 对每个图片文件都分配新 `String`，而后续仅用于简单的 `match` 比较。当目录中有数百张图片时会产生数百次不必要的堆分配。

**当前代码**：
```rust
if let Some(extension) = image_path.extension() {
    let ext = extension.to_string_lossy().to_lowercase();

    match ext.as_str() {
        "png" => compress_png(image_path, create_new_file, original_size),
        "jpg" | "jpeg" => compress_jpg(image_path, create_new_file, original_size),
        _ => Err(Error::compression(format!("不支持的图片格式: {}", ext))),
    }
}
```

**优化方案**：使用 `eq_ignore_ascii_case` 零分配比较：
```rust
if let Some(extension) = image_path.extension() {
    let ext = extension.to_string_lossy();
    let ext_str = ext.as_ref();

    if ext_str.eq_ignore_ascii_case("png") {
        compress_png(image_path, create_new_file, original_size)
    } else if ext_str.eq_ignore_ascii_case("jpg") || ext_str.eq_ignore_ascii_case("jpeg") {
        compress_jpg(image_path, create_new_file, original_size)
    } else {
        Err(Error::compression(format!("不支持的图片格式: {}", ext_str)))
    }
}
```

**影响范围**：`compress_pictures` crate，批量压缩数百张图片时可避免数百次 `String` 分配。

### 任务 23：`STREAMING_THRESHOLD` 常量虚设

**文件**：`crates/compress_pictures/src/lib.rs:11,172,224`

**问题**：定义了 `STREAMING_THRESHOLD = 10MB`，但在 `compress_png` 和 `compress_jpg` 中仅打印警告消息，未实现任何实际的流式处理逻辑。PNG 压缩（oxipng）和 JPEG 解码（image crate）都需要将完整文件读入内存，阈值检查毫无意义且误导性。

**当前代码**：
```rust
const STREAMING_THRESHOLD: u64 = 10 * 1024 * 1024; // 10 MB

fn compress_png(...) -> Result<f64> {
    if original_size as u64 > STREAMING_THRESHOLD {
        println!("文件大小超过阈值，使用缓冲IO处理: {}", image_path.display());
    }
    // ... 始终全量读取文件
}
```

**优化方案**：移除 `STREAMING_THRESHOLD` 常量及其检查，或用大文件警告替代（不声称有流式处理）：
```rust
// 方案 A：完全移除
fn compress_png(image_path: &Path, create_new_file: bool, original_size: f64) -> Result<f64> {
    let file = fs::File::open(image_path)?;
    let mut reader = BufReader::new(file);
    let mut input_data = Vec::new();
    reader.read_to_end(&mut input_data)?;
    // ...
}

// 方案 B：改为大文件警告（不声称"流式"）
const LARGE_FILE_THRESHOLD: u64 = 50 * 1024 * 1024; // 50 MB
if original_size as u64 > LARGE_FILE_THRESHOLD {
    println!("⚠️  警告：大文件 {} ({:.1} MB)，压缩可能较慢",
        image_path.display(), original_size / 1_048_576.0);
}
```

**影响范围**：`compress_pictures` crate，消除误导性日志输出。

### 任务 24：`mp4_to_m3u8` 中 tokio 依赖未使用 workspace

**文件**：`crates/mp4_to_m3u8/Cargo.toml:8`

**问题**：该 crate 独立声明 `tokio = { version = "1.0", features = [...] }` 而未使用 `{ workspace = true }`，导致：
1. tokio 版本与 workspace 声明不一致时可能产生重复编译
2. 违反 "workspace deps 统一管理" 约定
3. workspace 的 tokio features 为 `["process", "rt-multi-thread", "macros"]`，此 crate 额外需要 `"time"` feature

**当前代码**：
```toml
[dependencies]
tokio = { version = "1.0", features = ["process", "rt-multi-thread", "macros", "time"] }
```

**优化方案**：根据 Cargo 文档，workspace dep 追加 feature 使用 `{ workspace = true, features = [...] }` 会合并而非覆盖：
```toml
[dependencies]
tokio = { workspace = true, features = ["time"] }
```

同时检查其他 crate 是否也有独立声明 tokio 的情况。

**影响范围**：`mp4_to_m3u8` crate，依赖管理一致性。

### 任务 25：`get_video_duration` 未使用 `ffmpeg-sidecar` 封装的 ffprobe

**文件**：`crates/mp4_to_m3u8/src/lib.rs:232-266`

**问题**：`get_video_duration` 直接调用 `std::process::Command::new("ffprobe")` 获取视频时长，但项目已依赖 `ffmpeg-sidecar` crate（支持自动下载和管理 ffmpeg/ffprobe 二进制）。应使用 `ffmpeg_sidecar::command::ffprobe_command()` 确保使用与 ffmpeg 一致的 ffprobe 路径。

**当前代码**：
```rust
fn get_video_duration(mp4_file: &Path) -> Result<f64> {
    let output = std::process::Command::new("ffprobe")
        .args([...])
        .output();
    // ...
}
```

**优化方案**：
```rust
use ffmpeg_sidecar::command::ffprobe_command;

fn get_video_duration(mp4_file: &Path) -> Result<f64> {
    let output = ffprobe_command()
        .args([...])
        .output();
    // ...
}
```

**影响范围**：`mp4_to_m3u8` crate，确保使用 `ffmpeg-sidecar` 下载管理的 ffprobe 而非系统 PATH 中的随机版本。

## 🟡 中优先级

### 任务 26：dev-dependencies 版本不一致

**文件**：`crates/clear_node_modules/Cargo.toml:14`、`crates/clear_lock/Cargo.toml:12`

**问题**：两个 crate 使用 `tempfile = "3.5.0"`，而根 `Cargo.toml` 的 `[dev-dependencies]` 使用 `tempfile = "3.10"`。虽然 Cargo 会自动选择符合所有约束的最高版本，但显式版本不一致增加了维护者的认知负担。

**优化方案**：统一为最新版本或在 workspace 中定义共享 dev-dependency：
```toml
# clear_node_modules/Cargo.toml
[dev-dependencies]
tempfile = "3.10"

# clear_lock/Cargo.toml
[dev-dependencies]
tempfile = "3.10"
```

或（更优）在根 workspace 定义：
```toml
# 根 Cargo.toml [workspace.dependencies]
tempfile = "3.10"
```

然后在 crate 中引用：
```toml
[dev-dependencies]
tempfile = { workspace = true }
```

**影响范围**：`clear_node_modules`、`clear_lock` crate。

### 任务 27：多个 crate 缺少 `license` 字段

**文件**：`crates/compress_pictures/Cargo.toml`、`crates/mp4_to_m3u8/Cargo.toml`、`crates/gitignore_add_zip/Cargo.toml`

**影响范围**：3 个 crate 的 `Cargo.toml`，发布合规性。

### 任务 28：clap `message` 默认值可在声明层设置

**文件**：`src/main.rs:47-49`、`src/modules/git_ops.rs:7`

**问题**：`message` 参数的默认值 `"feat: update"` 在 `git_ops.rs` 中用 `unwrap_or` 处理，而 clap 支持 `default_value` 属性在声明层直接设置，更符合声明式 CLI 设计理念。

**当前代码**：
```rust
// main.rs
#[arg(short = 'm', long, value_name = "MESSAGE")]
message: Option<String>,

// git_ops.rs
let msg = message.unwrap_or("feat: update");
```

**优化方案**：
```rust
// main.rs
#[arg(short = 'm', long, value_name = "MESSAGE", default_value = "feat: update")]
message: String,

// git_ops.rs
let msg = &message; // 或直接传递 message.as_str()
```

**影响范围**：`main.rs`、`git_ops.rs`，代码整洁度。

### 任务 29：`vite_pack_add_zip` 正则 `unwrap()` 可用 `expect()`

**文件**：`crates/vite_pack_add_zip/src/lib.rs:8,11,14`

**问题**：三个 `LazyLock<Regex>` 的初始化使用 `Regex::new(...).unwrap()`，若正则语法错误会在运行时 panic 且无上下文。正则编译失败属于编译期可检测的 bug，应使用 `expect` 提供调试信息。

**优化方案**：
```rust
static OUT_DIR_RE: LazyLock<Regex> = LazyLock::new(|| {
    Regex::new(r#"(outDir\s*[:=]\s*['"]?)([^,'"}\s]+)['"]?"#)
        .expect("OUT_DIR_RE 正则编译失败")
});
```

**影响范围**：`vite_pack_add_zip` crate，调试体验。

### 任务 30：依赖版本可升级

**文件**：`Cargo.toml`

**问题**：部分 workspace 依赖版本非最新，升级可获得性能改进和 bug 修复：

| 依赖 | 当前版本 | 可升级至 | 收益 |
|------|----------|----------|------|
| `clap` | 4.4 | 4.5 | `default_value_t`、`help_expected`、更快的解析 |
| `regex` | 1.10.3 | 1.11+ | 编译时正则优化、`RegexSet` 改进 |

**优化方案**：批量更新 `[workspace.dependencies]` 中版本号，运行 `cargo update` 后执行完整测试。

**注意**：`regex 1.11+` 有 API 兼容性，直接升级即可。`clap 4.4 → 4.5` 可能有少量弃用警告需处理。

**影响范围**：全项目，编译速度、运行时性能。

### 任务 32：`is_ffmpeg_available` 可使用 `ffmpeg-sidecar` API

**文件**：`crates/mp4_to_m3u8/src/lib.rs:220-229`

**问题**：`is_ffmpeg_available` 通过 `std::process::Command` 检查 ffmpeg，而 `ffmpeg-sidecar` 提供了更可靠的检查方法（如 `ffmpeg_is_installed()` 或通过其版本管理机制）。

**优化方案**：使用 `ffmpeg_sidecar::command::FfmpegCommand::new().version()` 或直接依赖 `ensure_ffmpeg_available` 中的 `auto_download` 机制（当 ffmpeg 不可用时自动下载）。实际上 `ensure_ffmpeg_available` 已做了双重检查，`is_ffmpeg_available` 可内联简化：

```rust
async fn ensure_ffmpeg_available() -> Result<()> {
    // 先尝试运行 ffmpeg -version（快速路径）
    if std::process::Command::new("ffmpeg")
        .args(["-version"])
        .stdout(std::process::Stdio::null())
        .stderr(std::process::Stdio::null())
        .status()
        .map(|s| s.success())
        .unwrap_or(false)
    {
        return Ok(());
    }
    // 否则自动下载
    // ... 现有下载逻辑
}
```

**影响范围**：`mp4_to_m3u8` crate。

### 任务 33：`git_add_commit_push` 中 `Stdio::inherit` 可能干扰 CI 输出

**文件**：`crates/git_add_commit_push/src/lib.rs:13-14,44-47`

**问题**：`git add` 和 `git push` 使用 `Stdio::inherit()` 将输出直接传送到父进程。在 CI 环境或脚本中，这些输出可能扰乱日志解析。建议提供 `--quiet` 选项或统一使用 `.output()` 捕获。

**当前代码**：
```rust
let add_status = Command::new("git")
    .arg("add").arg(".")
    .current_dir(path)
    .stdout(Stdio::inherit())
    .stderr(Stdio::inherit())
    .status()?;
```

**优化方案**（保持向后兼容）：保持当前行为，但在文档中说明。或统一改为 `.output()` 仅在失败时打印 stderr。

**影响范围**：`git_add_commit_push` crate。
